## 0. Ground rules (recap)

| Rule | What it means in practice |
|---|---|
| **Agent, not workflow** | The LLM picks every tool call. My code = tools + loop + limits + logging. If I catch myself writing `if step == 2: call git_log()`, that's a workflow. |
| **Single agent** | No planner/executor split, no fixer, no verifier. Future work only. |
| **Read-only & bounded** | Tools can't write anything. Max 15 steps, per-tool timeout, output capped at ~100 lines. |
| **Static snapshots** | The agent reads `scenarios/<name>/` only. Ground truth lives in `ground_truth/`, physically unreachable by tools. |
| **I write what matters** | Claude Code works in **Learning mode**: it scaffolds files and plumbing, but leaves the decisions that matter as `TODO(human)` gaps for me (see §0.2). Claude Code is also the mentor: day briefings, concepts, reviews, debugging (no separate chat). Target app and scenarios are fully AI-generated. |
| **~2 weeks** | 12 working days + 2 buffer/polish days. If a day overruns, cut scope from the "Stretch" column, never from evaluation. |

### 0.2 Ownership split — what Claude Code may generate vs. `TODO(human)`

Rule of thumb: **if it's a design decision about how the agent thinks, acts, stops or is judged, it's mine.** If it's plumbing, it can be generated.

| Mine — `TODO(human)` | Generated by Claude Code |
|---|---|
| Loop control logic: message handling, tool dispatch, stop conditions, step limit, forced final report | Target app, faults, capture scripts, scenarios, ground truth |
| Tool **descriptions, arg schemas, "use this when…" hints, error messages** | File reading/parsing inside tools, path/cap/timeout helpers (I review them) |
| Output filtering/summarization choices (what `log_stats` returns, caps, defaults) | Pydantic/JSON-schema boilerplate, tool registry wiring |
| System prompt + baseline prompt | Provider wrapper boilerplate (`llm.py`) |
| Duplicate-call detection, report validation & retry policy | Trajectory JSON writer, eval runner plumbing (parallelism, folders) |
| Metric definitions: correctness rule, evidence check, calibration | Markdown/report formatting, plots |
| Failure analysis, tuning decisions, results interpretation | Trajectory viewer UI (I review structure, Tailwind can be generated) |

If Claude Code fills one of my gaps by accident: ask it to revert that part to a `TODO(human)` with a hint.

## 1. Decisions taken in this roadmap (open points closed)

### 1.1 Raw tool-calling loop first — LangGraph optional at the end
- **Why:** the whole point is learning agent engineering. A ~50–80 line loop forces me to understand messages, tool calls/results, stop conditions and state. With LangGraph this is hidden behind nodes/edges, and a graph also tempts you into hard-coding steps (= workflow).
- **Interview answer:** "I built the loop by hand to control limits, duplicate detection and trajectory logging exactly; a framework would add value for checkpointing, human-in-the-loop or multi-agent, which were out of scope."
- **Stretch (Day 14):** port the loop to a single-node LangGraph `create_react_agent`-style graph in ~half a day and write 5 lines on the trade-off. Only if everything else is done.

### 1.2 LLM provider strategy
- **Development:** one cheap / free-tier model with solid tool calling (e.g. a Gemini Flash-class model or a Groq-hosted open model). Check current rate limits and pricing before starting — they change often.
- **Final evaluation:** one stronger model, fixed and pinned (exact model version string in the results table). Optionally also report the dev model → this gives a "model size vs. agent performance" result for free.
- **Thin provider wrapper:** a single function `llm_call(messages, tools) -> (assistant_msg, usage)` so switching provider is one file. No LiteLLM/LangChain abstraction needed.
- **Budget:** log tokens per call from Day 3. Estimate total eval cost on Day 8 before the full run: `scenarios × 3 runs × 2 systems × avg tokens`.

### 1.3 Tool list (v1 — 7 tools + 1 terminal tool)
Every tool: typed args, JSON-schema description with a "Use this when…" hint, path confined to the current scenario folder, output capped, helpful errors ("No logs for service 'chekout'. Available services: api, worker, db").

| Tool | Signature (sketch) | Use this when… |
|---|---|---|
| `log_stats` | `(service, bucket="1m", since=None, until=None)` → counts per level + top error messages per bucket | you need **when** errors started and what dominates, before reading raw lines |
| `search_logs` | `(service, level=None, keyword=None, since=None, until=None, limit=50)` | you need the exact log lines (evidence) |
| `list_commits` | `(since=None, path=None, limit=20)` → hash, time, author, message, files changed | you want to know what changed recently / around the incident time |
| `show_commit` | `(hash, path=None, max_lines=100)` → diff | you suspect a specific change |
| `read_config` | `(name)` + listing when name missing | env vars, pool sizes, timeouts, feature flags |
| `get_db_schema` | `(table=None)` → tables, columns, indexes | you suspect migration / index / schema mismatch |
| `get_container_status` | `(service=None)` → state, restarts, exit code, OOMKilled, memory limit | crashes, restarts, resource issues |
| `submit_report` | `(root_cause_category, summary, evidence[], confidence, suggested_fix, status)` | terminal tool: ends the investigation |

`submit_report` as a **tool** (not free text) = structured output enforced by schema + a clean stop condition. `status ∈ {identified, not_identified}`.

Root-cause categories (fixed list, used by the report and the evaluator):
`missing_migration, bad_config, resource_exhaustion, performance_regression, code_bug, dependency_failure, infra_crash, unknown`

### 1.4 UI scope
React (Vite) + TypeScript + Tailwind, **read-only trajectory viewer**: pick a trajectory JSON → vertical timeline (hypothesis → tool call → truncated result) → final report card → eval verdict. No backend needed (load JSON files statically). Max ~1.5 days.

## 4. Day-by-day plan

Each day: **Learn** (concepts, ~1h) → **Build** → **Deliverable** (concrete, checkable) → **Done when**.

---

### Day 1 — Environment & first scenarios
**Prerequisite:** Day 0 setup (§0.1, `SETUP.md`) done. CP0 ticked.

**Learn**
- Agent vs. workflow (Anthropic's "Building effective agents" framing): who decides control flow?
- How tool calling works at the API level: `tools` schema → model returns tool calls → you execute → you append tool results → call again.
- What makes a good RCA scenario: symptom/cause separation, noise, red herrings, no giveaways.

**Build**
- Write the Claude Code brief for the target app (FastAPI + Postgres + Compose, JSON logs, traffic generator, ~10 realistic commits).
- Have Claude Code generate the app, the capture script and **3 easy + 2 medium** faults: missing migration, wrong env var, pool exhaustion, dropped index, OOM restart.
- **Review every scenario manually** (this is my job, not the AI's): grep for giveaways in commit messages, file names, comments.
- Make one ground-truth schema: `{category, key_detail, culprit_commit?, culprit_file?, difficulty, red_herrings[]}`.

**Deliverable:** `scenarios/` with 5 folders + `ground_truth/` with 5 JSON files.
**Done when:** I can solve each scenario myself by hand in < 10 minutes and the cause is NOT in the same file as the symptom.

---

### Day 2 — Tools
**Learn**
- Tool design = interface design for an LLM: names, descriptions, arg types, "use this when…", examples.
- Observation design: why summaries/counts beat raw dumps; context window budget.
- Safety: path confinement (no `../` escaping to `ground_truth/`), read-only, timeouts, output caps.
- Tool outputs are untrusted input (logs could contain prompt injection) → interview point.

**Build**
- `agent/tools/`: the 7 tools + `submit_report` schema (Pydantic models for args). File parsing can be scaffolded; descriptions, hints, defaults and error messages are `TODO(human)`.
- A registry: `name → (function, json_schema)`, generated from Pydantic where possible.
- Shared guards: `safe_path(scenario_dir, rel)`, `cap_output(text, max_lines=100)` with a "… 340 more lines, narrow with keyword/time window" footer, timeout wrapper.
- Unit tests: each tool on 1 scenario; one test proving `ground_truth/` is unreachable.

**Deliverable:** `pytest` green; a small script that calls each tool by hand on scenario 1 and prints outputs.
**Done when:** every output fits in ~100 lines and error messages tell the model what to do next.

---

### Day 3 — The loop (first autonomous run)
**Learn**
- ReAct pattern: reason → act → observe. Why we ask for a short "current hypothesis" before each call.
- Stop conditions: terminal tool, step limit, error budget.
- Message history as the agent's state; what grows and why it matters for cost.

**Build**
- `llm.py`: provider wrapper returning message + token usage.
- `loop.py` (~50–80 lines; Claude Code scaffolds the skeleton, the control logic is `TODO(human)`):
  - system prompt + incident text → loop until `submit_report` or 15 steps
  - execute tool calls, append results, handle unknown tool / bad args gracefully (return an error as the tool result, don't crash)
  - on step limit: force a final `submit_report` (with `status=not_identified` allowed)
- `trajectory.py`: save every step `{step, hypothesis, tool, args, result_preview, tokens, latency_ms}` + final report → JSON.
- System prompt v1: role, method (hypothesize → verify → conclude), constraints (read-only, evidence mandatory, "not identified" is acceptable).

**Deliverable:** `python -m agent.run scenarios/missing_migration` produces a trajectory JSON.
**Done when:** the agent reaches `submit_report` on at least 1 scenario on its own — even with a wrong answer.

---

### Day 4 — Structured report + ✅ CHECKPOINT 1
**Learn**
- Structured outputs: schema-enforced via tool args vs. "please answer in JSON".
- Hallucination in agents: claims not grounded in observations. Why evidence must be verbatim.
- Temperature 0 is *not* fully deterministic → why we do 3 runs.

**Build**
- Pydantic validation of `submit_report`; if invalid, return the validation error to the model (self-correction, 1 retry max).
- Duplicate-call detection: same tool + same args → return "You already ran this; result was X. Try a different angle." (counts as a step).
- Run on all 5 scenarios, read every trajectory, write a short failure note per scenario in `PROGRESS.md`.

**Deliverable:** 5 trajectories + 5 reports in `runs/`.
**✅ CP1 — Done when:** end-to-end works on 5 scenarios; ≥ 2 correct is fine at this stage. **What matters is that the loop, limits, logging and report all work.**

---

### Day 5 — Evaluation harness v0
**Learn**
- Evaluating agents: outcome metrics (accuracy) vs. process metrics (steps, cost, tool usage).
- Exact match vs. rubric vs. LLM-as-judge; why judge only borderline cases.
- Calibration: confidence vs. correctness; why "not identified" can be the right answer.

**Build**
- `eval/run_all.py`: N scenarios × K runs → `runs/<date>/agent/...`
- `eval/metrics.py`:
  - **category correct** (exact) + **key detail correct** (substring/normalized match against ground truth; flag unclear ones for judge)
  - **evidence check**: every quoted evidence string must appear verbatim in some tool result of that trajectory → `evidence_precision`
  - steps, tokens in/out, cost estimate, wall-clock latency
  - calibration buckets: accuracy per confidence level; rate of `not_identified`
- `eval/report.py` → markdown table per scenario + aggregate.

**Deliverable:** one command prints a results table for the 5 scenarios.
**Done when:** the evidence check catches at least one deliberately fabricated quote (write a fake trajectory to test it).

---

### Day 6 — More scenarios + failure analysis
**Learn**
- Error analysis: read trajectories, build a failure taxonomy (wrong tool, anchoring, gave up early, looped, hallucinated evidence, context drowning).
- Train/test split for prompts: **dev scenarios** (you tune on them) vs. **held-out scenarios** (you never look at them while tuning) → avoids overfitting the prompt to the test set. Strong interview point.

**Build**
- Claude Code: add ~7 scenarios (target total ~12), including first **hard** ones (cause 2 hops away, red herring with a plausible-looking error, cause in config diff inside an unrelated-sounding commit).
- Manual giveaway review again.
- Tag each scenario `dev` or `holdout` in ground truth (~60/40). Do NOT read holdout trajectories in detail until Day 9.
- Run eval on dev set, fill a failure taxonomy table in `PROGRESS.md`.

**Deliverable:** ~12 scenarios, failure taxonomy with counts.
**Done when:** I can name the top 2 failure modes with trajectory examples.

---

### Day 7 — Targeted mitigations + ✅ CHECKPOINT 2 (+ buffer)
**Learn**
- Prompt-level vs. tool-level vs. loop-level fixes — prefer fixing tools/observations before adding prompt rules.
- Anchoring and confirmation bias in agents; "verify before concluding" as a requirement, not a step.

**Build** (only for failure modes actually observed on Day 6)
- Anti-anchoring: prompt requires checking timing alignment (when did errors start vs. commit/deploy/config time) and state (schema/containers) before `submit_report`.
- If context drowning: improve `log_stats`, tighten defaults.
- If wrong tool choice: rewrite descriptions/hints, better error messages.
- If early give-up: allow `not_identified` only after ≥ N distinct tools *or* add "what have you not checked yet?" nudge at step 10. (Careful: a nudge is fine; forcing a tool order is a workflow.)
- Remaining time = buffer to catch up.

**Deliverable:** before/after table on dev set.
**✅ CP2 — Done when:** `make eval` (or one command) runs ~12 scenarios × 3 runs and outputs the metrics table.

---

### Day 8 — Full scenario set + baseline
**Learn**
- Why a baseline is the central result: an agent only matters if it beats a cheaper non-agent approach on something.
- Fair baseline design: same model, same info budget where possible.

**Build**
- Claude Code: finish to **15–20 scenarios**, balanced easy/medium/hard, red herring in every medium/hard.
- `baseline/`: one LLM call with `incident.txt` + last N log lines (error-level + window around the incident) + recent commit list + (optionally) diffs, truncated to a fixed token budget, same `submit_report` schema.
- Plug baseline into the eval runner as a second system.
- **Cost estimate** for the full eval with the final model; adjust runs or model if needed.

**Deliverable:** 15–20 scenarios; `eval --system baseline` works.
**Done when:** baseline produces valid reports on all scenarios.

---

### Day 9 — Full evaluation run (dev model)
**Learn**
- Reporting results honestly: per-difficulty breakdown, variance across runs, failure cases shown, not hidden.
- Cost/latency trade-off: the agent costs more — when is it worth it?

**Build**
- Run agent + baseline, all scenarios, 3 runs each.
- Results table: accuracy (overall / easy / medium / hard), evidence precision, not-identified rate, avg steps, tokens, cost, latency.
- **Now** open holdout trajectories and do failure analysis on them.

**Deliverable:** `results/dev_model.md`.
**Done when:** I can state in one sentence where the agent beats the baseline and where it doesn't.

---

### Day 10 — One tuning round + ✅ CHECKPOINT 3
**Learn**
- Diminishing returns & overfitting: one disciplined iteration, measured on dev, confirmed on holdout.

**Build**
- Apply max 2–3 changes driven by Day 9 failures (dev set only), re-run, compare.
- Freeze agent version v1.0 (git tag). No more prompt changes after this, except bug fixes.

**Deliverable:** v1.0 tag + updated results.
**✅ CP3 — Done when:** agent vs. baseline table exists on the full set, with dev/holdout split visible.

---

### Day 11 — Trajectory viewer UI
**Learn**

**Build**

- Views: scenario list with verdict (✅/❌/❓) → timeline (hypothesis → tool + args → collapsible result) → report card (cause, evidence highlighted, confidence, fix) → ground truth side-by-side.

**Deliverable:** viewer working on local trajectories.
**Done when:** a non-technical person can follow one investigation step by step.

## 5. Mitigations → where they are built

| Pain point | Mitigation | Day |
|---|---|---|
| Hallucinated causes | `submit_report` schema, mandatory evidence, `not_identified` allowed | 3–4 |
| Hallucinated evidence | Verbatim evidence check against tool outputs | 5 |
| Loops / repetition | 15-step limit, duplicate-call detection, hypothesis before each call | 3–4 |
| Context overflow | Filters (level/keyword/time), 100-line cap, `log_stats` summaries | 2, 7 |
| Bad tool choice | Clear names, "use this when…", helpful errors | 2, 7 |
| Anchoring | Required verification (timing + state) before concluding | 7 |
| Unsafe actions | Read-only tools, path confinement, timeouts | 2 |
| Prompt injection via logs | Tool outputs treated as data; no tool can act on them anyway | 2 (discuss in README) |
| Overfitting prompts to tests | Dev/holdout split | 6 |
| Hard to demo | Trajectory JSON from Day 3, viewer, video | 3, 11, 13 |

## 6. Interview questions to be able to answer (fill in as you go)

1. Why is this an agent and not a workflow? Show where the control flow decision is made.
2. Why a raw loop and not LangGraph? What would make you switch?
3. How do you stop the agent from looping, hallucinating, or doing something dangerous?
4. How did you design the tools? Example of a description you rewrote and why.
5. How do you evaluate an agent? Why a baseline? Why 3 runs at temperature 0?
6. How do you know the evidence is real?
7. What is your agent's worst failure mode? Show a trajectory.
8. What did the agent do better than the baseline, concretely, on hard scenarios? At what cost?
9. How did you avoid overfitting your prompt to your test scenarios?
10. What would you build next (multi-agent fixer/verifier, live environment) and what new risks would that bring?
